**Version:** 2.0  
**Organization:** CSEC-ASTU  
**Last Updated:** 2026-11-11

## 📌 1. Introduction

### 1.1 Purpose

This document defines the full software requirements for the CSEC-ASTU Bootcamp Management System (BMS) v2.0. It supersedes SRS v1.0 entirely. The BMS is the operational backbone of CSEC-ASTU's training and induction pipeline — managing the full lifecycle from public applicant registration through bootcamp delivery to formal Division membership induction.

### 1.2 Scope

The BMS is a purpose-built internal platform for CSEC-ASTU. It is **not** a multi-tenant SaaS product. It supports:

- Four permanent Divisions: **Data Science**, **Development**, **CPD**, **Cybersecurity**
- Time-bound **Bootcamp** cohorts run under each Division
- A structured student induction funnel: `GUEST → APPLICANT → STUDENT → DIVISION MEMBER`
- Role-scoped access for Super Admins, Division Admins (Division Heads), Instructors, and Students

### 1.3 Key Definitions

| Term | Definition |
| ------ | ----------- |
| **Division** | A permanent organizational track within CSEC-ASTU (e.g. Development). Never deleted. |
| **Bootcamp** | A time-bound training cohort created under a Division (e.g. *Dev Cohort 2026*). Owns all sessions, tasks, groups, and attendance. |
| **Guest** | A registered user who has not yet enrolled in any Bootcamp. |
| **Applicant** | A Guest who has submitted an application to a Bootcamp and is awaiting screening. |
| **Student** | An Applicant who has been accepted into a Bootcamp by a Division Admin. |
| **Division Member** | A Student who has completed a Bootcamp and been formally inducted into the Division. |
| **Instructor** | A user assigned to deliver sessions and grade tasks in a specific Bootcamp. |
| **Division Admin** | A user with administrative authority scoped to their Division (equivalent to Division Head). |
| **Super Admin** | Platform-wide administrator with override authority on all divisions and bootcamps. |
| **Milestone Task** | A group deliverable tied to a phase of the Bootcamp capstone project. |
| **Individual Task** | A personal assignment graded per student independently. |
| **Attendance Code** | A time-limited code generated by the Instructor to open a check-in window for a session. |
| **Induction** | The formal promotion of a Student to Division Member at the end of a Bootcamp. |

### 1.4 Assumptions

- All users have internet access and a modern browser.
- Students have or can create a Telegram account for notifications.
- The club operates on a semester or cohort-based calendar.
- Physical sessions occur on the ASTU campus (shared spaces across all divisions).

## 👥 2. User Roles & Lifecycle

### 2.1 Role Definitions

Roles in BMS v2 are **context-scoped** — a user may hold different roles in different contexts, except for `SUPER ADMIN` which is global.

| Role | Scope | Authority |
| ------ | ------- | ----------- |
| `SUPER ADMIN` | Global | Full platform override on all divisions, bootcamps, users, and sessions |
| `DIVISION ADMIN` | Per Division | Division Head authority — manages bootcamps, instructors, applicants, induction decisions within their Division |
| `INSTRUCTOR` | Per Bootcamp | Assigned to specific Bootcamps — creates sessions (pending approval), grades tasks, opens attendance |
| `STUDENT` | Per Bootcamp | Enrolled in a specific Bootcamp — attends sessions, submits tasks, participates in group |
| `GUEST` | Global | Registered but not yet enrolled in any Bootcamp — can browse open Bootcamp applications |

> A user can hold multiple roles simultaneously in different contexts. For example: a user can be a `DIVISION ADMIN` in Development and a `STUDENT` in a CPD Bootcamp.

### 2.2 Student Lifecycle State Machine

```text
[Public Sign-Up]
       ↓
    GUEST
       ↓  (applies to open Bootcamp)
  APPLICANT
       ↓  (Division Admin accepts)
   STUDENT  ←→  (active in Bootcamp)
       ↓  (Bootcamp ends, Admin inducts)
DIVISION MEMBER
```

**Additional states:**

- `APPLICANT_REJECTED` — application declined by Division Admin
- `STUDENT_DROPPED` — removed from Bootcamp mid-way
- `NOT_INDUCTED` — completed Bootcamp but not accepted into Division

## 🔐 3. Authentication & Security

### 3.1 Registration & Login

- **Public Sign-Up:** Any person can register with `fullName`, `email`, `password`, `universityId`, `department`, and an optional Telegram username.
- Registered users start with the `GUEST` role.
- Login via email and password.
- Passwords hashed with **bcrypt** (minimum 12 salt rounds).

### 3.2 Token Strategy

- **Access Token:** JWT, 24-hour expiry.
- **Refresh Token:** Signed JWT, 7-day expiry, stored as an httpOnly cookie.
- Token rotation on refresh.

### 3.3 Security Rules

- Rate limiting: 5 failed login attempts → 15-minute lockout.
- Password reset via email link (1-hour expiry, single-use).
- All API responses strip secrets (password, refreshToken, reset tokens) via a shared allowlist sanitizer.
- Input validation on all endpoints (Zod schemas).
- TLS enforced in production.

## 🏗️ 4. Core Modules

### 4.1 Division Management

Divisions are permanent. Only `SUPER ADMIN` can create or archive a Division.

**Division data:**

- `name`, `slug`, `description`, `createdAt`
- Assigned `DIVISION ADMIN` user(s)

**Division Dashboard (visible to Division Admin & Super Admin):**

- Count of active Bootcamps
- Total enrolled / screened students across all bootcamps
- Average session attendance rate
- Average task completion rate
- Average session rating

---

### 4.2 Bootcamp Management

A **Bootcamp** is the central operational unit — it owns all learning activity.

**Bootcamp fields:**

- `title`, `division`, `description`
- `startDate`, `endDate`
- `applicationOpenDate`, `applicationCloseDate`
- `status`: `DRAFT` → `OPEN` (accepting applications) → `SCREENING` → `ACTIVE` → `COMPLETED`
- `maxApplicants` (optional cap)
- **Scoring weights** (configurable per Bootcamp):
  - `attendanceWeight` (default: 20%)
  - `individualTaskWeight` (default: 40%)
  - `groupMilestoneWeight` (default: 30%)
  - `peerReviewWeight` (default: 10%)
  - Weights must sum to 100%
- Assigned `INSTRUCTOR`(s)

**Bootcamp Dashboard (visible to Division Admin & Instructors):**

- Live leaderboard of all Students sorted by weighted score
- Group milestone progress tracker
- Attendance heatmap per session
- Task submission rates (% submitted, % graded)

---

### 4.3 Application & Screening

When a Bootcamp status is `OPEN`:

1. `GUEST` users see the Bootcamp listing and an **Apply** button.
2. Application form collects: `motivation` (text, ≥100 chars), `relevantExperience` (optional text), `linkedinOrGitHub` (optional URL).
3. Submission creates an `APPLICANT` record for that Bootcamp.
4. Division Admin receives a notification: *"New application submitted."*

**Screening phase (Bootcamp status: `SCREENING`):**

- Division Admin views ranked applicant list.
- Can **Accept** or **Reject** each applicant.
- Accepted → user's role for that Bootcamp transitions to `STUDENT`.
- Rejected → user receives notification: *"Your application to [Bootcamp] was not selected."*
- Accepted → user receives notification: *"Congratulations! You have been accepted into [Bootcamp]."*

---

### 4.4 Session Management

**Session fields:**

- `title`, `description`
- `bootcamp` (and therefore implicitly Division)
- `location` (physical address or online link)
- `startTime`, `endTime` (minimum duration: 30 minutes)
- `instructorId`
- `status`: `PENDING` | `APPROVED` | `CANCELLED` | `COMPLETED`

**Creation flow:**

1. Assigned `INSTRUCTOR` creates a session → status: `PENDING`.
2. `DIVISION ADMIN` reviews and **Approves** or **Rejects** with an optional note.
3. On approval: status → `APPROVED`, enrolled Students are notified.
4. `DIVISION ADMIN` can directly create sessions (auto-approved) or cancel any session.

**Conflict detection (enforced at proposal time):**

- **Global no-overlap rule:** No two sessions across any Division may share the same time slot.
- **Instructor double-booking:** An Instructor cannot be assigned to overlapping sessions.
- Sessions must be proposed at least **1 hour** before start time.

---

### 4.5 Attendance Management

Attendance is captured inside each session's **Attendance Tab**.

**Check-in flow:**

1. Instructor navigates to the Attendance Tab on a session page.
2. Clicks **"Open Attendance"** → system generates a time-limited **Attendance Code** (alphanumeric, e.g. `A7X9Q`) and starts a countdown timer (default window: **30 minutes**, configurable per session).
3. Code and a text input + Submit button appear on each enrolled Student's session view.
4. Student enters the code and submits:
   - Within window → **`PRESENT`**
   - After window, before code expiry → **`LATE`**
5. When the code expires → all Students who never submitted are auto-marked **`ABSENT`**.
6. Instructor can manually override any individual attendance status at any time (with an optional note).
7. Division Admin can override Instructor decisions.

**Attendance status types:**

- `PRESENT` — checked in within the window
- `LATE` — checked in after the window
- `ABSENT` — did not check in before code expiry
- `EXCUSED` — manually set by Instructor/Admin (requires a note)

**Rules:**

- One attendance record per Student per Session.
- Only Students enrolled in the Bootcamp tied to the Session can check in.

---

### 4.6 Resource Management

Instructors and Division Admins can upload or link resources against a Session or Bootcamp.

**Upload types:** PDF, Video, Image, ZIP  
**External links:** Supported (URL with title and description)  
**Tracking:** Download count per resource  
**Storage:** Local server storage (static file serving via Express/Multer) or free S3-compatible bucket (e.g. Supabase Free Tier)

---

### 4.7 Group Management

**Group formation:**

1. After Bootcamp enrollment closes, Students receive a **group formation window** (deadline set by Division Admin).
2. Within the window, Students can:
   - Create a group and invite peers by username or email.
   - Accept or decline an invitation.
3. Group size: **2–8 Students**.
4. After the formation deadline:
   - Ungrouped Students are flagged for the Instructor/Admin.
   - Instructor/Admin manually assigns remaining Students to existing groups or creates new ones.
5. Each group designates a **Group Leader** (the creator by default; can be reassigned by the Admin).

**Group rules:**

- One group per Student per Bootcamp.
- Group Leader can submit Milestone Tasks on behalf of the group.
- Any member can submit with Group Leader confirmation (or Admin override).

---

### 4.8 Task Management

The task system contains two distinct task types under a unified interface.

#### 4.8.1 Individual Task

Assigned to **all Students** in the Bootcamp.

**Fields:**

- `title`, `description`, `instructions`
- `submissionType`: `FILE` | `GITHUB_LINK` | `BOTH`
- `deadline`
- `maxScore`
- `allowLateSubmission` (bool) + `latePenaltyPercent` (optional)
- `allowResubmission` (bool)

**Workflow:**

- Each Student submits independently.
- Instructor grades per Student: `score`, written `feedback`, `qualitativeFlag` (Excellent / Satisfactory / Needs Improvement).
- Resubmissions tracked with version history.

#### 4.8.2 Group Milestone Task

Assigned to **Groups** as a phase of the Bootcamp Capstone Project.

**Fields:**

- `title`, `description`, `milestoneNumber` (e.g. 1, 2, 3, Final)
- `submissionType`: `FILE` | `GITHUB_LINK` | `BOTH`
- `deadline`
- `maxScore`
- `peerReviewRequired` (bool)

**Workflow:**

1. Group Leader (or any member with Leader confirmation) submits on behalf of the group.
2. Submission includes individual **contribution notes** per member.
3. If `peerReviewRequired`: Peer Review requests are automatically sent to all group members post-submission.
4. Instructor grades the group submission → one `groupScore` issued.
5. Each member's milestone score = `groupScore` × peer review weight adjustment.

---

### 4.9 Submission System

**Common rules for all submissions:**

- No submission after deadline unless `allowLateSubmission` is enabled.
- GitHub links must match valid GitHub URL patterns.
- File uploads stored in local server filesystem (`uploads/`) with static serving (or free-tier bucket; size limit: 50 MB per file).
- Resubmission allowed (when enabled) with full version history preserved.

**Submission statuses:** `SUBMITTED` | `GRADED` | `RETURNED` (requires revision)

---

### 4.10 Feedback System

#### 4.10.1 Session Feedback (Student → Session)

- Eligible: Students marked `PRESENT` or `LATE` for the session.
- Window: 48 hours after session end time.
- One feedback per Student per Session.
- Fields: `rating` (1–5), `comment` (optional text).
- **Anonymous to Instructors** — Instructors see aggregate stats only.
- Division Admins see full disaggregated feedback.

#### 4.10.2 Peer Review (Student → Teammate)

- Triggered automatically when a Group Milestone Task is submitted (if `peerReviewRequired`).
- Each group member receives a Peer Review request for every other member.
- Fields: `rating` (1–5), `contributionComment` (optional text).
- **Anonymous to peers** — only Instructors and Division Admins can see individual peer review data.
- Peer review scores feed into each member's individual Milestone Task score adjustment.
- Window: 72 hours after Milestone submission.

#### 4.10.3 Instructor Feedback (Instructor → Student)

- Attached to each Individual Task grading action.
- Fields: `score`, `writtenFeedback` (text), `qualitativeFlag` (`EXCELLENT` | `SATISFACTORY` | `NEEDS_IMPROVEMENT`).
- Visible to the assessed Student only.

### 4.12 Reports & Analytics

- Count of active Bootcamps
- Total enrolled / screened students
- Average session attendance rate
- Average task completion rate
- Average session rating across all Bootcamps

#### Bootcamp Dashboard (Division Admin, Instructors)

### 4.13 Induction Management

At the end of an `ACTIVE` Bootcamp, the Division Admin initiates the induction process:

1. Bootcamp status transitions to `COMPLETED`.
2. System computes final weighted scores for all Students.
3. Division Admin views the **Induction Review Dashboard**:
   - Full ranked leaderboard with score breakdown per student.
   - Set a **cutoff threshold** (e.g. 70%) as a visual guide (not enforced automatically).
4. Division Admin marks each Student as:
   - **`INDUCTED`** → user transitions to `DIVISION MEMBER` of the Division.
   - **`NOT_INDUCTED`** → user transitions to `NOT_INDUCTED` status (retains GUEST role).
5. Admin can **override any decision freely** — accept a student below the cutoff or reject one above it — with an optional override note for accountability.
6. On confirmation: Inducted students receive a notification, and their role is promoted system-wide.

## ⚙️ 5. Business Rules

### Scheduling

- Global no-overlap: no two sessions across any Division may share any time window.
- Instructor cannot be double-booked.
- Sessions must be proposed at least 1 hour before start time.
- Sessions must have a minimum duration of 30 minutes.

### Attendance

- Unique attendance record per Student per Session.
- `EXCUSED` status requires a note.
- Attendance code window default: 30 minutes (configurable per session).

### Feedback

- Only `PRESENT` / `LATE` students may submit Session Feedback.
- One Session Feedback per Student per Session.
- Peer Reviews are due within 72 hours of Milestone submission.

### Tasks

- No submission after deadline unless `allowLateSubmission` is enabled.
- GitHub links must match a valid GitHub URL pattern.
- File upload limit: 50 MB per file.

### Groups

- Size: 2–8 Students.
- One group per Student per Bootcamp.
- Group formation deadline set by Division Admin per Bootcamp.

### Scoring

- Bootcamp scoring weights must sum to 100%.
- Weights are locked after Bootcamp transitions to `ACTIVE`.
- Peer review score adjustment cannot take a student's milestone score below 0 or above max.

### Applications

- Applications accepted only while Bootcamp status is `OPEN`.
- A Guest may apply to multiple Bootcamps in different Divisions simultaneously.

## 🗄️ 7. Database Design

**Database:** PostgreSQL  
**ORM:** Prisma

### Core Entities

| Entity | Key Relations |
| -------- | -------------- |
| `User` | Has many `UserRoles` (scoped), many `Enrollments`, many `Submissions` |
| `UserRole` | Belongs to `User`, scoped to `Division` or `Bootcamp` |

| `Group` | Belongs to `Bootcamp`, has many `GroupMembers` |
| `GroupMember` | Joins `User` ↔ `Group`, carries `isLeader` flag |
| `PeerReview` | Reviewer → Reviewee within a `Group`, scoped to `Task` |
| `SessionFeedback` | Belongs to `User` and `Session` |
| `Notification` | Belongs to `User`, carries `channel`, `readAt` |
| `InductionDecision` | Belongs to `Enrollment`, carries `decision`, `overrideNote`, `decidedBy` |
| `Resource` | Belongs to `Session` or `Bootcamp` |
| `AuditLog` | Tracks sensitive actions (overrides, induction decisions, role changes) |

## ⚠️ 9. Error Handling

| Code | Meaning |
| ------ | --------- |
| 400 | Validation Error — malformed request body |
| 401 | Unauthorized — missing or invalid token |
| 403 | Forbidden — authenticated but insufficient role/scope |
| 404 | Not Found |
| 409 | Conflict — e.g. scheduling overlap, duplicate attendance |
| 422 | Business Rule Violation — e.g. late submission not allowed, attendance window closed |

All error responses follow:

```json
{
  "status": "error",
  "code": 422,
  "message": "Human-readable description",
  "field": "fieldName (optional, for validation errors)"
}
```

## 🚀 10. Non-Functional Requirements

### Performance

- ≤ 300ms p95 response time for read operations
- ≤ 600ms p95 response time for write operations
- Leaderboard queries ≤ 500ms with up to 500 concurrent students

### Security

- TLS enforced in production
- Secure JWT handling (httpOnly cookies for refresh tokens)
- Input validation via Zod on all endpoints
- Allowlist sanitizer strips secrets from all User objects before API response
- Audit log for all sensitive actions (induction decisions, attendance overrides, role changes)

### Reliability

- 99.5% uptime target
- Database backups: daily automated, 30-day retention

### Scalability

- Stateless backend (no server-side session storage)
- Local disk / persistent volume uploads via Multer (or free S3/Supabase storage)
- PostgreSQL connection pooling (PgBouncer or Prisma connection pooling)
